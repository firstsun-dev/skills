# Notion Workstream

用一個 Notion Database 維護目前有效的工作脈絡與可執行任務。預設保持扁平、減少重複、讓階層規則可預期，並在任何寫入前由使用者確認。

## 核心原則

- **屬性保存可查詢狀態**：狀態、領域、關聯等資訊以 Database 屬性為準，不在正文重複維護。
- **Page 保存目前有效脈絡**：正文描述現在仍成立的目標、範圍、決策、限制與任務內容，不寫流水帳。
- **Comment 保存事件**：討論、AI 提問、使用者回覆、執行結果、Review、修正等依時間發生的資訊優先放 Comment。
- **預設扁平**：正常結構只需要 L1 工作脈絡與 L2 任務。AI 不自行增加更深層級。
- **先讀再做**：處理任務時讀取必要的上層脈絡，但不預設載入所有歷史。
- **先預覽再寫入**：任何 Notion 寫入都必須先顯示預計變更，取得使用者確認後才執行。

## Database 資料模型

常用屬性：

- `名稱`：row 標題。
- `領域`：分類、篩選、分組用的屬性。它與名稱、狀態等都存在同一筆 row，不參與 L1/L2/L3+ 階層。
- `狀態`：工作生命週期的唯一狀態來源。不要在正文另外維護進度摘要或狀態清單。
- `上級項目` / `子項目`：Notion 開啟 Sub-items 後自動新增、可重新命名的系統屬性，只用來表示工作階層。
- `最後更新`：最後編輯時間，用於排序與判斷新舊。

若既有 Database 已有清楚且等價的欄位名稱，沿用既有結構，不為了符合範例強制改名。

## 階層

```text
L1 工作脈絡
├─ L2 任務
├─ L2 任務
└─ L2 任務
   └─ L3+ 只有使用者明確要求子任務時才存在
```

L 層級只由 `上級項目` / `子項目` 的 Sub-items 階層決定。

`領域` 只是同一筆 row 的屬性，不是 L0，也不是父節點。

### L1：工作脈絡

L1 保存多個 L2 共同需要、而且目前仍有效的脈絡。

適合放：

- 目標與範圍；
- 已確認決策；
- 限制與不可破壞條件；
- 不容易從任務本身推斷、但所有子任務都需要知道的背景。

不要放：

- 可由 `狀態` 屬性直接看出的進度；
- 子任務狀態彙總；
- 為了同步而重複抄寫的 Database 屬性；
- 純時間序的工作日誌。

建立 L1 的時機：

- 使用者明確指定要建立一條工作脈絡時；
- AI 確實找不到合適的既有 L1 時，可以建議新增，但不得直接建立，必須先取得使用者確認。

### L2：任務

L2 是 L1 底下預設、正常、主要的執行單位。

每個 L2 應該：

- 單獨閱讀時就能理解要做什麼；
- 可以獨立執行、完成與 Review；
- 可以依賴 L1 的共享脈絡，但不應依賴 sibling 任務才能拼出自己的完整要求；
- 使用 `狀態` 屬性表示進度，不在正文維護第二份進度。

建立任務時，預設建立為 L2。

如果使用者要求把一個任務「拆分」成多個任務，預設以多個**同層任務取代原任務**，不要保留只剩總稱、沒有獨立資訊價值的父項。

只有使用者明確要求「子任務」時，才保留原任務並建立更深一層。

### L3+

L3 之後沒有新的特殊語意，仍然是任務。

但它不是預設規劃工具：

- AI 不得因為認為任務還能再拆，就自行新增 L3+；
- 只有使用者明確要求子任務，或既有資料本來就存在更深階層時才操作；
- 不要為了形式一致主動把既有結構加深或扁平化。

## Comment：保存事件

Comment 優先保存依時間發生、可能有歷史價值，但不應污染目前正文的資訊，例如：

- 人類與 AI 的討論；
- AI 提出的問題；
- 使用者實際給出的回答或決定；
- AI 的執行結果；
- Review 發現；
- 修正結果與後續觀察。

Comment 不屬於 L1/L2/L3+ 階層。

一般工作不需要先讀完所有 Comment。只有在目前 Page 不足以解釋規則、需求看似矛盾、需要知道「為什麼」、或使用者要求回顧歷史時，再讀相關 Comment。

如果 Comment 中形成一個之後仍然有效、後續工作必須知道的決策，再把該決策整理進適當的 Page 正文。不要把整段討論複製進正文。

## 讀取流程

處理某筆工作時：

1. 先讀目標 row。
2. 依 `上級項目` 向上讀取必要祖先，至少理解其所屬 L1 工作脈絡。
3. 若目前資訊已足夠，直接規劃或執行。
4. 只有遇到不清楚、矛盾、非直覺限制、需要歷史原因，或使用者明確要求時，才讀相關 Comment。
5. 不因為資料存在就預設讀取所有 sibling 或 Comment。

## CRUD 規則

### L1

- **Create**：使用者明確要求建立；或 AI 建議後取得使用者確認。
- **Read**：處理其下任務時讀取必要的共享脈絡。
- **Update**：共享的目前真相改變時更新，例如目標、範圍、決策、限制改變。
- **Delete**：只有使用者明確要求，並完成寫入確認流程後才刪除。

### L2

- **Create**：建立新的可獨立執行任務時。
- **Read**：讀取任務本身與必要祖先脈絡。
- **Update**：任務要求、有效決策、狀態或其他目前真相改變時。
- **Delete / Replace**：使用者明確要求刪除，或已確認以多個同層任務取代原任務時。

### L3+

CRUD 與任務相同，但只有使用者明確要求子任務或既有結構已存在時才使用。

### Comment

新增、修改或刪除 Comment 都屬於 Notion 寫入，同樣必須先預覽並確認。

## 寫入確認

讀取 Notion 不需要確認。

任何會改變 Notion 的操作都必須遵循：

```text
讀取必要資料
→ 顯示預計變更
→ 使用者確認
→ 執行已確認的變更
```

寫入包含但不限於：

- 建立 Page / row；
- 修改正文或屬性；
- 修改狀態；
- 新增、移除或改變關聯；
- 移動父項；
- 拆分、合併、取代或刪除任務；
- 新增、修改或刪除 Comment。

預覽應讓使用者能看出：要改哪個項目、改什麼、階層是否改變。

使用者確認後，只執行預覽過的範圍。如果執行前發現新資訊導致變更內容需要改動，重新預覽並再次取得確認。

## 正文寫法

不要強迫所有 L1 或 L2 使用固定 heading 模板。

正文只需要清楚保存目前有效的內容；依實際工作選擇必要段落即可。

優先更新既有內容，不要為每次變化追加一份新的狀態副本。

## 邊界

- 不把 `領域` 當成階層。
- `上級項目` / `子項目` 只表示工作階層。
- 不自行建立 L1。
- 不自行建立 L3+。
- 不在正文重複維護狀態或進度。
- 不為普通 AI 互動建立大量歷史 Page。
- 不要求每次工作都讀完整歷史。
- 不在未確認的情況下寫入 Notion。
- 不因為一般最佳實務與目前脈絡不同，就擅自改寫已確認的使用者決策。
